# Admin UI

Веб-интерфейс для просмотра процессов и ручного вмешательства. По умолчанию выключен; включается через
`ruslo.admin-ui.enabled=true`. Подключение, настройки и защита через Spring Security — в
[README модуля](https://github.com/neherim/ruslo/blob/main/ruslo-admin-ui/README.md).

## Страницы

- **Дашборд** (`/ruslo`): число процессов в `FAILED`, просроченных и активных, всего и по типам, и узлы движка с
  работающим диспетчером. Процесс просрочен, если он активен и его следующий запуск прошёл больше минуты назад:
  его не подхватывает ни один узел. Счётчик открывает соответствующий список процессов. Тип процесса показан с
  описанием, заданным `ProcessSpecBuilder.description(...)`.
- **Список процессов** (`/ruslo/processes`): поиск с фильтрами и массовые действия над всеми совпадениями.
- **Страница процесса**: статус, состояние, переменные, таймеры процесса, последняя ошибка, история состояний и
  диаграмма definition с пройденным путём. Пока процесс выполняется, страница обновляется.

## Действия

Меню Actions на странице процесса показывает все ручные действия, которые можно осуществить с процессом:

| Действие | Операция |
|---|---|
| Retry current step | `resumeFailedProcess`, для процесса в `FAILED` |
| Change state | `moveProcessToState` |
| Send message | `sendMessage`, с JSON payload, проверенным по классу payload |
| Add, edit, remove variable | `setProcessVariable`, `removeProcessVariable` |
| Set, cancel timer | `setProcessTimer`, `cancelProcessTimer`; момент — в часовом поясе браузера |

Каждое действие пишется в лог приложения с именем пользователя.

## Массовые действия

Меню **Bulk actions** в списке процессов применяет последние отправленные фильтры поиска ко **всем страницам**:

- **Retry all matching** требует фильтр статуса `FAILED`. Процессы возобновляются для диспетчера;
  действие не ждёт завершения их обработчиков.
- **Change state for all matching** требует один зарегистрированный тип процесса. Целевое состояние
  выбирается из определения этого типа, включая терминальные. Завершённые процессы пропускаются.

Перед подтверждением диалог показывает точное число процессов, применённые фильтры, распределение по
типу/состоянию/статусу и до двадцати примеров строк. Изменённые фильтры вступают в силу после отправки Search.
Подтверждённая выборка фиксирована: новые совпадения не добавляются. Процесс, изменивший состояние или статус
либо переставший соответствовать фильтру, пропускается после проверки под блокировкой его строки.

Прикладного лимита на число процессов нет. Действие выполняется последовательно с индикатором ожидания
и фиксирует каждый процесс отдельной транзакцией. Неожиданная ошибка останавливает операцию; предыдущие
успешные изменения сохраняются. В диалоге показаны успехи, пропуски с причинами и процесс, исход изменения
которого нужно проверить после прерывания. При потере HTTP-ответа сервер может продолжать операцию:
проверьте процессы перед новым запуском. Браузер не повторяет запрос автоматически.

Для массовых действий нужен bean `Database` движка. Стандартный starter предоставляет его; ручная сборка
движка и ограничения окружения для длительных запросов описаны в
[README модуля](https://github.com/neherim/ruslo/blob/main/ruslo-admin-ui/README.md#bulk-operations).

## Диаграмма процесса

Диаграмма строится по definition: состояния подписаны `ProcessState.description()` (по умолчанию имя состояния), переходы — результатом, именем
сообщения или таймером. Легенда — в [README модуля](https://github.com/neherim/ruslo/blob/main/ruslo-admin-ui/README.md#process-diagram).

Переходам с ветвлением можно задать подпись через `routes.on(outcome, target, "Подпись")` — в шагах и событиях
await. На схеме подпись заменяет имя outcome; имена сообщений и таймеры остаются видны.
Без подписи показывается имя outcome.

```java
.step(VALIDATING, validateStep, routes -> routes
    .on(Validation.VALID, RESERVING, "Проверка пройдена")
    .on(Validation.REJECTED, CANCELLED, "Проверка не пройдена"))
```
