# Ожидания

Ожидание (`await`) останавливает процесс, пока не наступит одно из объявленных событий: придёт сообщение или
сработает таймер. Ожидание может длиться минуты или месяцы; пока процесс ждёт, он не занимает ни поток, ни
соединение с БД.

## События ожидания

| Событие | Срабатывает |
|---|---|
| `message(type, handler, target)` | когда приходит сообщение типа `type` |
| `every(interval, handler, target)` | регулярно, каждые `interval` |
| `after(delay[, handler], target)` | один раз, через `delay` после входа в ожидание |
| `at(timer[, handler], target)` | в момент таймера процесса `timer` |

`target` — целевое состояние или маршруты по результату обработчика (`routes -> routes.on(...)`), см.
[переходы](processes.md#переходы). Каждый вид таймера объявляется в ожидании не больше одного раза.

```java
.await(WAITING_FOR_PAYMENT, await -> await
    .message(PAYMENT_CONFIRMED, PaymentDefinition::onPaid, SHIPPING)
    .every(Duration.ofDays(1), PaymentDefinition::remind, WAITING_FOR_PAYMENT)   // ежедневное напоминание
    .at(PAYMENT_DUE, CANCELLED))                                               // срок, который задаёт код
```

Обработчики событий:

| Событие | Линейный обработчик | Ветвящийся обработчик |
|---|---|---|
| `message` | `ProcessMessageHandler<T>` | `BranchingMessageHandler<T, O>` |
| `every`, `after`, `at` | `ProcessTimerHandler` | `BranchingTimerHandler<O>` |

У `after` и `at` обработчик необязателен: без него событие сразу переводит процесс в `target`. Обработчики ожидания
всегда выполняются на транзакционном worker `DEFAULT` ([workers.md](workers.md)).

## Сообщения

Тип сообщения задаёт имя и класс payload:

```java
public static final MessageType<PaymentConfirmed> PAYMENT_CONFIRMED =
        MessageType.of("payment", PaymentConfirmed.class);

static void onPaid(ProcessContext context, IncomingMessage<PaymentConfirmed> message) {
    context.setVariable(PAYMENT_ID, message.payload().paymentId());
}
```

Обработчик получает `IncomingMessage<T>` с payload и временем получения. Сообщение отправляют по id процесса:

```java
processEngine.sendMessage(processId, PAYMENT_CONFIRMED, new PaymentConfirmed("txn-42"));
```

Если известен только ключ из предметной области, сначала найдите процесс по `businessKey`
([operations.md](operations.md#поиск-процессов)).

### Когда сообщение принимается

- `sendMessage` принимает сообщение, только если процесс сейчас в ожидании, которое объявляет его тип. Иначе
  (ожидание ещё не началось, уже закончилось или процесс завершён) он бросает `MessageNotExpectedException` с текущим
  состоянием процесса и ничего не сохраняет.
- **Ранние сообщения не буферизуются**: отправитель повторяет позже или игнорирует отказ. Перехват отказа не откатывает
  транзакцию вызывающего ([spring.md](spring.md#транзакции-приложения)).
- Тип сообщения, который не объявлен ни в одном ожидании процесса, — ошибка вызывающего: `IllegalArgumentException`.
- Процесс в `FAILED` принимает сообщения своего ожидания; они обрабатываются после `resumeFailedProcess`.
- Внутри `@Transactional` приложения `sendMessage` атомарен с его данными: при откате сообщение не сохраняется.

### Что гарантирует принятое сообщение

- Успех означает, что сообщение сохранено в очереди процесса, **а не** что его обработчик будет вызван: если другое
  событие раньше выведет процесс из ожидания, необработанные сообщения удаляются (см.
  [выход из ожидания](#остаться-в-ожидании-или-выйти)).
- Сообщения одного процесса обрабатываются по одному, в порядке поступления. Обработчик выполняется в одной
  транзакции с удалением сообщения из очереди.
- **`sendMessage` не идемпотентен**: повторная отправка того же payload ставит в очередь второе сообщение. Если
  отправитель может повторить вызов, обработчик распознаёт дубликаты, например по id в payload (рецепт `webhook`).
- Движок не хранит историю сообщений: сообщение удаляется после обработки.

## Таймеры ожидания: `every` и `after`

`every` и `after` относятся к одному входу в ожидание; движок задаёт их, когда процесс входит в него.

- `after(delay)` срабатывает один раз, через `delay` после входа.
- `every(period)` срабатывает по фиксированной сетке от входа: `firstAfter + k * period` (`firstAfter` по умолчанию
  равен `period`). Опоздавшая проверка не сдвигает сетку, а точки, пропущенные за время простоя, не выполняются
  пачкой: выполняется одна проверка, дальше сетка продолжается. Чтобы сдвинуть первую проверку, передайте `Interval`
  вместо `Duration`. Например, чтобы выполнить `every` сразу при входе:
  `every(Interval.of(period).firstAfter(Duration.ZERO), handler, target)`.

Опоздавшая проверка `every` видит текущее состояние внешней системы, которое могло измениться после точки сетки.

## Таймеры процесса: `at`

`at(T)` ждёт именованный таймер процесса (`TimerType`). В отличие от `every` и `after`, таймером управляет
пользовательский код: задаёт, сдвигает и отменяет его.

```java
static final TimerType PAYMENT_DUE = TimerType.of("paymentDue");

static void reserve(ProcessContext context) {                      // шаг перед ожиданием
    context.setTimer(PAYMENT_DUE, context.now().plus(Duration.ofDays(5)));
}

static void extend(ProcessContext context, IncomingMessage<Instant> message) {   // цель — само ожидание
    context.setTimer(PAYMENT_DUE, message.payload());
}
```

Таймер процесса состоит из имени и момента срабатывания. Правила:

1. **Таймер принадлежит процессу.** У процесса может быть несколько таймеров с разными именами. Таймер с одним
   именем либо не задан, либо задан на один момент срабатывания; `setTimer` для заданного таймера заменяет его
   момент срабатывания.
2. **Таймер задают и отменяют код и оператор.** При запуске процесса — `newProcess(...).timer(...)`, в обработчиках —
   `ProcessContext.setTimer` и `ProcessContext.cancelTimer`, вручную — через `ProcessEngineAdmin` или Admin UI.
   Изменение действует сразу, без повторного входа в ожидание. Движок сам таймер не задаёт; он только отменяет
   сработавший таймер (пункт 5).
3. **Таймер срабатывает только в ожидании с `at`.** Таймер срабатывает, когда процесс находится в ожидании с `at`,
   а момент срабатывания не позже времени движка (`ProcessContext.now()`). Если момент срабатывания уже прошёл к
   моменту входа в такое ожидание, таймер срабатывает сразу. Пока таймер не задан, он не срабатывает.
4. **Переходы не меняют таймер.** Таймер остаётся заданным, пока не сработает или не будет отменён. Это верно и
   когда процесс вышел из ожидания с `at` по другому событию этого ожидания (`message`, `after`, `every`): тогда
   таймер сработает в следующем ожидании с `at` с тем же именем.
5. **Сработавший таймер отменяется после обработчика `at`.** Пока выполняется обработчик `at`, таймер остаётся
   заданным, и `getTimer` возвращает его момент срабатывания. После обработчика движок отменяет таймер, если
   обработчик не задал ему новый момент срабатывания; тот же момент новым не считается. Если обработчик задал новый
   момент, таймер остаётся заданным на него. Если обработчик завершился ошибкой, его изменения откатываются, и
   повторная попытка видит таймер таким же. У `at` без обработчика таймер отменяется при срабатывании.

Сдвигая таймер в обработчике, можно построить расписание:

```java
.await(SCHEDULED, await -> await
    .at(NEXT_RUN, ReportDefinition::buildReport, routes -> routes
        .on(Run.MORE, SCHEDULED)
        .on(Run.LAST, DONE)))

static Run buildReport(ProcessContext context) {
    var runAt = context.getTimer(NEXT_RUN).orElseThrow();         // момент срабатывания
    // построить отчёт за runAt
    context.setTimer(NEXT_RUN, runAt.plus(Duration.ofDays(1)));
    return Run.MORE;
}
```

Считайте следующий момент от момента срабатывания, а не от `context.now()`: тогда опоздавший запуск не сдвигает
расписание. Полные примеры — рецепты `deadline` и `subscription` в
[`ruslo-examples/cookbook`](https://github.com/neherim/ruslo/tree/main/ruslo-examples/cookbook).

## Остаться в ожидании или выйти

Событие, целью которого указано само ожидание, оставляет процесс ждать: обработанное сообщение удаляется, остальные
сообщения в очереди и таймеры сохраняются ([переход в то же состояние](processes.md#переходы)).

Переход в другое состояние закрывает ожидание, и **его необработанные сообщения удаляются**. Чтобы начать ожидание
заново, с пустой очередью и новыми таймерами `every` и `after`, пройдите через шаг, который ведёт обратно в него:

```java
.await(ACTIVE, await -> await
    .message(ACTIVITY, Session::onActivity, RECORDING_ACTIVITY)   // сообщение ACTIVITY перезапускает таймаут
    .after(Duration.ofMinutes(30), EXPIRED))
.step(RECORDING_ACTIVITY, Session::recordActivity, ACTIVE)
```

## Какое событие обрабатывается

Один запуск ожидания обрабатывает **одно** событие. У каждого события есть время:

- сообщение — момент, когда `sendMessage` его сохранил;
- `every` — его точка сетки;
- `after` — вход в ожидание плюс `delay`;
- `at` — момент таймера процесса.

Событие наступило, если его время не позже часов движка. Из наступивших обрабатывается событие с самым ранним
временем; при равенстве порядок такой: сообщение, `every`, `after`, `at`, а сообщения — в порядке поступления. Когда
диспетчер добрался до процесса, значения не имеет.

Обработанное событие расходуется в транзакции обработчика: сообщение удаляется, `every` переходит к следующей точке
сетки после текущего момента, `after` выключается до нового входа в ожидание, а таймер `at`, который обработчик не
сдвинул, отменяется. Если обработчик упал, всё это откатывается вместе с ним, и повтор выбирает то же событие.

Пример: `after(1h)` от входа в ожидание в 11:00, срок — 12:00.

| Ситуация | Результат |
|---|---|
| Сообщение принято в 11:59, обработка началась в 12:01 | обрабатывается сообщение: оно раньше срока |
| Сообщение принято в 11:59 и обработано с целью — само ожидание | `after` срабатывает сразу после него |
| Сообщение принято в 12:00:30, обработка началась в 12:01 | срабатывает `after`; сообщение удаляется вместе с очередью |
| Сообщение принято в 11:59, его обработка упала, повтор в 12:05 | сообщение повторяется в 12:05, `after` ждёт его (см. ниже) |

Таймеры никогда не срабатывают раньше своего времени, но могут опоздать на несколько секунд; от чего зависит
задержка — в [guarantees.md](guarantees.md#время).

## Ошибки в ожидании

Исключение обработчика откатывает его транзакцию, и дальше действует [политика ошибок](error-handling.md). В ожидании
у повтора есть особенность: **ошибка приостанавливает всё ожидание до времени повтора**. Новые сообщения и наступившие
таймеры не будят процесс. После паузы обрабатывается самое раннее наступившее событие, обычно упавшее. Поэтому
временный сбой задерживает обработку, но не меняет порядок событий.

Следствие: если сообщение, принятое в 11:59, продолжает падать, срок `after` в 12:00 ждёт его; при бесконечных
повторах срок не сработает никогда. Для жёсткого срока:

- ограничьте повторы (`ProcessErrorHandler.fixed(maxRetries, delay)` с `onGiveUp`);
- или перехватите ошибку в обработчике и верните результат, который оставляет процесс ждать.

Процесс в `FAILED` не обрабатывает события; после `resumeFailedProcess` снова действуют правила этой страницы.

## Синхронная обработка сообщения

`processEngine.sendMessageSync(processId, type, payload)` выполняет обработчик сообщения в вызывающем потоке и
транзакции (или в новой). Используйте его, когда вызывающему нужен зафиксированный переход до возврата из вызова,
например для отмены пользователем (рецепт `cancellation`).

- Синхронно выполняется только обработчик этого сообщения; следующие шаги диспетчер выполнит после commit.
- Сообщение обходит очередь: более ранние сообщения и наступившие таймеры продолжают ждать, а при переходе в другое
  состояние сообщения из очереди удаляются.
- Если процесс сейчас не ждёт этого сообщения, метод бросает `MessageNotExpectedException`; для процесса в `FAILED`
  тоже, с `getStatus() == FAILED`. Ничего не сохраняется.
- Исключение обработчика пробрасывается вызывающему и откатывает транзакцию: сообщение не сохраняется, политика
  ошибок не вызывается.
