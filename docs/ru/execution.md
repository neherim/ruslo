# Правила исполнения

Точные правила, на которых держатся [гарантии](guarantees.md): границы транзакций, порядок событий ожидания и
конкурентный доступ. Для обычных процессов эта страница не нужна; читайте её, когда важно время между событиями.

## Переходы

Каждый вызов обработчика завершается одной транзакцией, которая сохраняет новое состояние и изменения
`ProcessContext`. Следующий обработчик выполняется в новой транзакции. Если следующее состояние исполняется на том же
worker, процесс продолжает тот же узел; иначе процесс возвращается в общую очередь.

Исключение обработчика откатывает его транзакцию: изменения переменных не сохраняются, а обрабатывавшееся сообщение
или таймер остаётся для повтора. Дальше действует [политика ошибок](error-handling.md).

## Выбор события ожидания

Один запуск ожидания обрабатывает **одно** событие. У каждого события есть время:

- сообщение — момент, когда `sendMessage` его сохранил;
- `every` — его точка сетки;
- `after` — вход в ожидание плюс `delay`;
- `at` — момент таймера процесса.

Событие наступило, если его время не позже часов движка. Из наступивших обрабатывается событие с самым ранним
временем; при равенстве порядок такой: сообщение, `every`, `after`, `at`, а сообщения — в порядке поступления. Когда
диспетчер добрался до процесса, значения не имеет.

Обработанное событие расходуется в транзакции обработчика: сообщение удаляется, `every` переходит к следующей точке
сетки после текущего момента, `after` выключается до нового входа в ожидание, а таймер `at`, который обработчик не
сдвинул, отменяется. Если обработчик упал, всё это откатывается вместе с ним, и повтор выбирает то же событие.

### Повтор приостанавливает ожидание

Ошибка обработчика приостанавливает всё ожидание до времени повтора: новые сообщения и наступившие таймеры не будят
процесс. После паузы обрабатывается самое раннее наступившее событие, обычно упавшее. Поэтому временный сбой
задерживает обработку, но не меняет порядок событий.

Следствие: если сообщение, принятое в 11:59, продолжает падать, срок `after` в 12:00 ждёт его; при бесконечных
повторах срок не сработает никогда. Для жёсткого срока ограничьте повторы
(`ProcessErrorHandler.fixed(maxRetries, delay)` с `onGiveUp`) или перехватите ошибку в обработчике и верните
результат, который оставляет процесс ждать.

### Пример

`after(1h)` от входа в ожидание в 11:00, срок — 12:00:

| Ситуация | Результат |
|---|---|
| Сообщение принято в 11:59, обработка началась в 12:01 | обрабатывается сообщение: оно раньше срока |
| Сообщение принято в 11:59, его обработка упала, повтор в 12:05 | сообщение повторяется в 12:05, `after` ждёт его |
| Сообщение принято в 11:59 и обработано с целью — само ожидание | `after` срабатывает сразу после него |
| Сообщение принято в 12:00:30, обработка началась в 12:01 | срабатывает `after`; сообщение удаляется вместе с очередью |

Поэтому:

- успешный `sendMessage` не означает, что обработчик будет вызван: сообщение, принятое после срока, удаляется при
  переходе по сроку;
- опоздавшая проверка `every` видит текущее состояние внешней системы, которое могло измениться после срока;
- точки `every`, пропущенные за время простоя, не выполняются пачкой: выполняется одна проверка, дальше сетка
  продолжается;
- процесс в `FAILED` не обрабатывает события; после `resumeFailedProcess` снова действуют эти правила.

## Конкурентный доступ

Процессом в каждый момент владеет один узел. Транзакционный worker держит блокировку строки процесса, пока работает
обработчик, поэтому параллельный `sendMessage` ждёт commit перехода и видит либо старое ожидание, либо новое
состояние. Нетранзакционный worker блокировку не держит: перед сохранением результата движок проверяет, что процесс
всё ещё принадлежит этому узлу и не изменился; иначе результат отбрасывается, и шаг выполняется снова.

Если узел не продлевал регистрацию дольше `ruslo.dispatcher.instance-timeout`, его процессы забирают другие узлы.
Таймаут измеряется временем базы данных, поэтому расхождение часов узлов на него не влияет. Результаты шагов,
начатых потерянным узлом, отбрасываются.

## Синхронная обработка сообщения

`processEngine.sendMessageSync(processId, type, payload)` выполняет обработчик сообщения в вызывающем потоке и
транзакции (или в новой). Используйте его, когда вызывающему нужен зафиксированный переход до возврата из вызова,
например для отмены пользователем (рецепт `cancellation`).

- Синхронно выполняется только обработчик этого сообщения; следующие шаги диспетчер выполнит после commit.
- Сообщение обходит очередь: более ранние сообщения и наступившие таймеры продолжают ждать, а при переходе в другое
  состояние сообщения из очереди удаляются.
- Если процесс сейчас не ждёт этого сообщения, метод бросает `MessageNotExpectedException`; для процесса в `FAILED`
  тоже, с `getStatus() == FAILED`. Ничего не сохраняется.
- Исключение обработчика пробрасывается вызывающему и откатывает транзакцию: сообщение не сохраняется, политика
  ошибок не вызывается.
