# Гарантии

На что можно рассчитывать при использовании движка. Точные правила — в [execution.md](execution.md).

## Главное

- **Каждый переход фиксируется отдельной транзакцией.** При сбое повторяется только тот обработчик, переход которого
  не зафиксирован.
- **Внешние вызовы выполняются хотя бы один раз — в любом режиме worker.** Если узел упал или транзакция откатилась
  после HTTP-запроса или отправки в Kafka, шаг будет выполнен снова. Делайте внешние вызовы идемпотентными.
- **Шаги одного процесса не исполняются параллельно, и переход сохраняет только один узел.** Исключение: если узел
  завис дольше `instance-timeout` посреди шага на нетранзакционном worker, процесс подхватит другой узел, и шаг может
  выполниться дважды; результат зависшего узла будет отброшен.
- **Процесс не теряется при падении узла.** Его подхватит другой узел через `ruslo.dispatcher.instance-timeout`
  (по умолчанию 60 секунд).

## Режимы worker

| | `transactional` (по умолчанию) | `non_transactional` |
|---|---|---|
| Изменения в БД приложения из шага | атомарны с переходом: фиксируются ровно один раз | не атомарны: повторяются при повторе шага |
| Внешние вызовы (HTTP, брокеры) | хотя бы один раз | хотя бы один раз |
| Соединение с БД во время шага | занято | не занято |
| Для чего | короткая логика и работа с БД | долгие внешние вызовы |

«Атомарны» — при том же `DataSource` и transaction manager. Обработчики сообщений и таймеров всегда исполняются на
транзакционном `DEFAULT`. Назначение worker — в [workers.md](workers.md).

## Сообщения

- `sendMessage` принимает сообщение, только если процесс сейчас в ожидании, которое объявляет его тип. Иначе
  (ожидание ещё не началось, уже закончилось или процесс завершён) он бросает `MessageNotExpectedException` с текущим
  состоянием процесса и ничего не сохраняет. **Ранние сообщения не буферизуются**: отправитель повторяет позже или
  игнорирует отказ. Перехват не откатывает транзакцию вызывающего
  ([spring.md](spring.md#транзакции-приложения)).
- Тип сообщения, который не объявлен ни в одном ожидании процесса, — ошибка вызывающего: `IllegalArgumentException`.
- Процесс в `FAILED` принимает сообщения своего ожидания; они обрабатываются после `resumeFailedProcess`.
- Успех означает, что сообщение сохранено, **а не** что его обработчик будет вызван: если другое событие раньше
  выведет процесс из ожидания, необработанные сообщения удаляются.
- **`sendMessage` не идемпотентен**: повторная отправка того же payload ставит в очередь второе сообщение. Если
  отправитель может повторить вызов, обработчик распознаёт дубликаты, например по id в payload (рецепт `webhook`).
- Обработчик сообщения выполняется в одной транзакции с удалением сообщения из очереди, а сообщения одного процесса
  обрабатываются по одному, в порядке поступления.
- Внутри `@Transactional` приложения `sendMessage` и `newProcess(...).start()` атомарны с его данными.

## Время

- Таймеры (`every`, `after`, `at`, `retryAfter`) никогда не срабатывают раньше своего времени. Обычно они
  срабатывают почти вовремя; задержка может достигать `ruslo.dispatcher.max-interval` (по умолчанию 10 секунд), если
  таймер запланировал другой узел, и быть больше, если не хватает ёмкости worker.
- Новый процесс или сообщение обычно подхватывается сразу после commit.
- Время событий измеряется `Clock` движка на каждом узле: расхождение часов узлов размывает границу «сообщение пришло
  до срока».

## Чего движок не делает

- Не хранит версии definition: изменение кода затрагивает запущенные процессы, см.
  [эволюцию definition](concepts.md#эволюция-definition).
- Не хранит историю сообщений: сообщение удаляется после обработки.
- Не удаляет завершённые процессы, см. [эксплуатацию](operations.md#хранение-завершённых-процессов).
- Не поддерживает параллельные ветви внутри одного процесса: разбивайте работу на отдельные процессы (рецепт `fanout`).
