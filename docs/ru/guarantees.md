# Гарантии

[English](../guarantees.md) | Русский

Сводка того, на что можно рассчитывать при использовании движка. Подробности исполнения — в [execution.md](execution.md),
ошибок — в [error-handling.md](error-handling.md).

## Главное

- **Каждый переход фиксируется отдельной транзакцией.** После commit состояние и переменные процесса сохранены;
  при сбое повторяется только тот обработчик, переход которого не зафиксирован.
- **Внешние вызовы выполняются хотя бы один раз — в любом режиме worker.** Если узел упал или транзакция откатилась
  после HTTP-запроса или отправки в Kafka, шаг будет выполнен снова. Делайте внешние вызовы идемпотентными.
- **Шаги одного процесса не исполняются параллельно, и результат перехода сохраняет только один узел.**
  Исключение: если узел завис дольше `instance-timeout` посреди шага на нетранзакционном worker, процесс
  подхватит другой узел, и шаг какое-то время может выполняться дважды; результат зависшего узла будет отброшен.
- **Процесс не теряется при падении узла.** Его подхватит другой узел примерно через
  `ruslo.dispatcher.instance-timeout` (по умолчанию 60 секунд).

## Режимы worker

| | `transactional` (по умолчанию, `DEFAULT`) | `non_transactional` |
|---|---|---|
| Изменения в БД приложения из шага (тот же `DataSource` и transaction manager в Spring) | атомарны с переходом: фиксируются ровно один раз | не атомарны с переходом: при повторе шага выполнятся снова |
| Внешние вызовы (HTTP, брокеры) | хотя бы один раз | хотя бы один раз |
| Изменения `ProcessContext` | атомарны с переходом | сохраняются вместе с переходом; если узел потерял процесс (пауза дольше `instance-timeout`), отбрасываются, и шаг повторяется |
| Соединение с БД во время шага | занято всё время шага | не занято |
| Для чего | короткая логика и работа с БД | долгие внешние вызовы |

Обработчики сообщений и таймеров всегда исполняются на транзакционном `DEFAULT`.
Как назначить шагу другой worker — в [workers.md](workers.md).

## Сообщения

- `sendMessage` принимает сообщение, только если процесс сейчас находится в ожидании, объявившем этот тип.
  Иначе (ожидание ещё не началось, уже закончилось или процесс завершён) метод бросает
  `MessageNotExpectedException` с текущим состоянием процесса и ничего не сохраняет. **Ранние сообщения не буферизуются**: отправитель повторяет отправку с задержкой или использует
  transactional outbox.
- Отказ в приёме бросается после выхода из транзакции движка, поэтому перехваченный отказ транзакцию вызывающего
  кода не трогает: например, шаг, который отчитывается уже завершённому родителю, перехватывает
  `MessageNotExpectedException` и продолжает работу. Неперехваченный отказ — обычная ошибка шага или
  транзакции приложения.
- Тип сообщения, не объявленный ни в одном ожидании процесса (или объявленный с другим классом payload), — ошибка
  вызывающего кода: `IllegalArgumentException`, транзакция помечается для отката.
- Процесс в `FAILED` принимает сообщения своего ожидания: они ждут в очереди и обрабатываются после `resumeFailedProcess`.
- Успешный возврат `sendMessage` означает, что сообщение сохранено, но **не** что его обработчик будет вызван.
  Если раньше сработает другое событие ожидания (например, `timeout`) и процесс уйдёт из ожидания,
  необработанные сообщения удаляются.
- **`sendMessage` не идемпотентен.** Повторная отправка того же payload кладёт в очередь второе сообщение.
  Если отправитель может повторить вызов (например, после timeout), обработчик должен распознавать дубликаты,
  например по идентификатору в payload.
- Обработчик сообщения выполняется в транзакции вместе с удалением сообщения из очереди: его изменения в БД
  и в `ProcessContext` фиксируются ровно один раз.
- Сообщения одного процесса обрабатываются по одному в порядке поступления.
- Вызов внутри `@Transactional` приложения атомарен с его данными: при rollback сообщение не сохраняется.
  То же относится к `newProcess(...).start()`.

## Время

- Таймеры (`timeout`, `every`, `retryAfter`) срабатывают не раньше назначенного времени.
  Перед паузой диспетчер узнаёт из БД срок ближайшего процесса и просыпается к нему, поэтому на простаивающем
  узле таймер срабатывает почти точно в срок. Опоздание до `ruslo.dispatcher.max-interval`
  (по умолчанию 10 секунд) возможно, если таймер назначен на другом узле, пока этот спал, а сам тот узел
  его взять не может. При нехватке ёмкости worker таймер срабатывает, когда она освободится.
- Новый процесс или сообщение диспетчер узла, который их сохранил, обычно подхватывает сразу после commit.
- Время событий считается по `Clock` движка на каждом узле. При расхождении часов узлов граница
  «сообщение пришло до дедлайна» размыта на величину расхождения.

## Чего движок не делает

- Не хранит версию definition: изменение кода шага влияет на уже запущенные процессы,
  см. [эволюцию definition](concepts.md#эволюция-definition).
- Не хранит историю сообщений и их payload: после обработки сообщение удаляется.
- Не удаляет завершённые процессы, см. [эксплуатацию](operations.md#хранение-завершённых-процессов).
- Не выполняет шаги одного процесса параллельно и не поддерживает параллельные ветки.
