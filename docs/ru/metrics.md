# Метрики

Spring Boot starter регистрирует метрики Micrometer при наличии `MeterRegistry`. При запуске без Spring можно передать
реализацию `ProcessEngineMetrics` в builder.

## Процессы и шаги

| Метрика                          | Тип                               | Смысл                                                                                                               |
|----------------------------------|-----------------------------------|---------------------------------------------------------------------------------------------------------------------|
| `ruslo.processes.started`        | Counter, `type`                   | Счетчик запусков процессов                                                                                          |
| `ruslo.processes.completed`      | Counter, `type`                   | Счетчик завершенных процессов                                                                                        |
| `ruslo.processes.failed`         | Counter, `type`                   | Счетчик процессов перешедших в статус `FAILED`                                                                      |
| `ruslo.processes.steps.duration` | Timer, `type`, `state`, `outcome` | Длительность шагов процесса. `outcome=success` - обработчик успешно завершился, `outcome=error` - бросил исключение |
| `ruslo.processes`                | Gauge, `status`                   | Число процессов в статусах `ACTIVE` и `FAILED`                                                                      |
| `ruslo.system.errors`            | Counter                           | Ошибки самого движка, не связанные с вашими обработчиками (обычно недоступность БД)                                 |

Метрика привязывается к состоянию, обработчик которого был вызван. Число ошибок видно по `outcome=error`, остановки - по
`processes.failed`. Отдельного счетчика ошибок нет: `count` метрики `ruslo.processes.steps.duration` с `outcome=error` -
это число ошибок обработчиков.

## Workers

| Метрика                 | Тип                 | Смысл                                                                                                                                                   |
|-------------------------|---------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------|
| `ruslo.worker.capacity` | Gauge, `worker`     | Максимум одновременно исполняемых шагов (`max-concurrency`)                                                                                             |
| `ruslo.worker.active`   | Gauge, `worker`     | Исполняемые сейчас шаги на этом узле                                                                                                                    |
| `ruslo.worker.ready`    | Gauge, `worker`     | Процессы worker'а, готовые к исполнению, но ещё не взятые ни одним узлом                                                                                |
| `ruslo.worker.lag`      | TimeGauge, `worker` | Сколько ждёт исполнения самый старый из них. Ноль, если таких нет                                                                                       |
| `ruslo.lease.lost`      | Counter             | Результаты шагов, отброшенные из-за потери владения процессом (например, после паузы узла дольше `instance-timeout`). Такой шаг будет выполнен повторно |

`worker.lag` - основной сигнал застоя: он растёт, если диспетчер остановился или ёмкости не хватает. 
`worker.ready` и `worker.lag` - общие для кластера значения из БД, поэтому каждый экземпляр показывает одно и то же.

## Стоимость gauges

Gauges `processes`, `worker.ready` и `worker.lag` выполняют запрос к БД при каждом чтении registry (например, при scrape
Prometheus) на каждом экземпляре: два запроса на `processes` и по два на каждый worker. Запросы используют индексы и не
читают завершённые процессы.

## Собственная реализация

Контракт расширения находится в `io.github.neherim.ruslo.core.spi.ProcessEngineMetrics`. Все callbacks имеют
default-реализацию без действий; можно переопределить только нужные метрики. Исключения в callbacks перехватываются и не
нарушают выполнение процессов. Suppliers, переданные в `register*`, храните по сильной ссылке: движок не держит их у
себя.
